## 一、硬件搭建阶段

### 问题 1：点阵完全不亮，代码反复检查无果

- **现象**：程序烧录后点阵没有任何显示，但用 LED 替换点阵后 LED 正常亮
- **环境**：AT89C52 + 8×8 点阵，Keil 编译，串口下载
- **排查过程**：
  1. 最先怀疑代码 —— 检查 `Display_Num()` 的行选/列选逻辑，扫描顺序正确
  2. 验证 P2 行选 —— 用示波器/万用表测各行输出电压，行选有波形
  3. 验证 P0 列选 —— **发现 P0 各脚始终为低电平，无波形**
  4. 查 8051 手册 —— P0 是**开漏输出**，内部无上拉电阻
- **根本原因**：P0 作为通用 IO 输出高电平时，必须外接上拉电阻（本设计用 10K×8 阵列），否则无法拉高
- **解决方法**：在 P0 各列线上并联 10K 上拉电阻阵列
- **收获**：**51 单片机的 P0 口是开漏输出，这是和 STM32 最大的差别之一**。硬件不工作时，先怀疑引脚电气特性，再怀疑代码

### 问题 2：蜂鸣器发声微弱且有杂音

- **现象**：蜂鸣器声音很小，混有明显杂音
- **排查过程**：
  1. 测 P1.0 输出波形，方波正常
  2. 怀疑是占空比不对 → 改用 50% 占空比，杂音减轻但音量仍小
  3. 测蜂鸣器两端电压，发现只有约 0.8V
- **根本原因**：蜂鸣器电流超出 MCU 引脚直接驱动能力（8051 单脚灌电流上限约 10mA），MCU 输出高电平时压降严重
- **解决方法**：加 NPN 三极管 + 基极限流电阻，由 MCU 只提供基极电流，集电极回路供电给蜂鸣器
- **收获**：**MCU 引脚不是电源**。凡是超过几十 mA 的负载，必须加驱动电路 —— 这一条在后面做电机驱动时是同样的原理

## 二、软件调试阶段

### 问题 3：播放到曲目末尾后越界访问，程序跑飞

- **现象**：前两首曲子播放正常，切到第三首时程序行为异常（音符乱跳或直接死机）
- **排查过程**：
  1. 发现只要把第三首数组长度改短，异常就消失 → 确认是越界
  2. 定位到数组末尾的判断条件：
     ```c
     if (idx >= sizeof(song1)) { idx = 0; }   /* ❌ 侥幸没出错 */
     ```
  3. 分析 `sizeof` 语义 —— `sizeof(数组名)` 返回的是**整个数组占用的字节数**，不是元素个数
- **根本原因**：`sizeof(song1)` = 元素数 × 2 字节，所以边界判断比实际宽松了将近一倍，**属于"侥幸正确"**。当换用元素类型不同的数组时立刻失效
- **解决方法**：
  ```c
  if (idx >= sizeof(song1) / sizeof(song1[0])) { idx = 0; }   /* ✅ */
  ```
  元素个数 = 总字节数 ÷ 单个元素字节数
- **收获**：**`sizeof` 有三种完全不同的行为，数组名传参时会退化成指针**。这类"看起来对"的代码最危险，因为一换场景就崩

### 问题 4：Keil 打开工程报错找不到源文件

- **现象**：工程能打开，但编译时提示找不到 `main.c`
- **排查过程**：
  1. 确认文件确实在 `Firmware/User/` 目录下
  2. 打开 `atm89.uvproj`，发现文件路径写的是 `.\MusicBox_Keil_Project\main.c` —— 这是**项目改名前的旧目录名**
- **根本原因**：工程文件里存的是**相对路径**，重命名/移动项目目录后路径失效
- **解决方法**：把工程文件中的路径改为 `..\User\main.c`，与实际目录结构对齐
- **收获**：Keil 工程文件的路径是相对的，**项目文件夹整体改名后一定要检查工程文件里的路径**

### 问题 5：RAM 不够，程序跑飞

- **现象**：加入第三首曲子后程序跑飞，加载后随机重启
- **排查过程**：
  1. 看编译输出的 RAM 使用量，已经接近 128B 上限
  2. 检查变量声明，发现乐谱数组没有加 `code`
- **根本原因**：8051 内部 RAM 只有 128 字节。乐谱数组不加 `code` 会被放进 RAM，几百字节的常量表直接把内存撑爆
- **解决方法**：所有常量表加 `code` 关键字
  ```c
  gequ code bad_apple[] = { ... };
  ```
- **收获**：**8051 有 code/data/xdata 三个独立存储空间，"数据放在哪"是 51 开发的第一课**。这跟"内存不够就加个数组"的直觉是反的

### 问题 6：音调明显不准

- **现象**：蜂鸣器发声但音调与预期差得远，且同一个音在不同曲目里音高不一致
- **排查过程**：
  1. 用示波器测 P1.0 输出频率，与目标频率对比
  2. 检查频率计算公式，发现漏掉了 8051 的 **12 分频**
- **根本原因**：8051 的机器周期 = 12 个振荡周期。最初按 `1/晶振` 算周期，**漏了 12 倍系数**
- **解决方法**：
  ```
  机器周期 = 12 / 11.0592MHz ≈ 1.085μs
  半周期计数 = 65536 - 装载值
  中断周期 = 半周期计数 × 1.085μs
  蜂鸣器频率 = 1 / (2 × 中断周期)
  ```
  全部音符装载值重算
- **收获**：**不同架构的定时器时基公式不一样，不能套用**。51 是 12 分频，STM32 直接按内核时钟算

### 问题 7：中断后音调忽高忽低

- **现象**：播放过程中偶尔出现一个明显走音的音符，随后恢复正常
- **排查过程**：
  1. 怀疑定时器重装载不准确 —— 检查发现 T0 采用**模式 1（16 位）**，重装载需要分两次写 TH0 和 TL0
  2. 意识到问题不在重装载值本身，而在**中断服务程序执行时间**：
     ```c
     void t0_isr(void) interrupt 1 {
         SPEAKER = ~SPEAKER;
         TH0 = current_period >> 8;     /* 重新装载 */
         TL0 = current_period & 0xFF;
     }
     ```
     如果 ISR 里还做了别的事（当时把显示刷新也放进来了），中断周期就被拉长，音调随之偏移
- **根本原因**：ISR 里混入了显示刷新等耗时操作，导致中断间隔不稳定
- **解决方法**：ISR 只保留"翻转 + 重装载"两件事，显示刷新全部放回主循环
- **收获**：**中断服务程序的第一原则是短**。这是嵌入式里最普适的性能直觉之一

## 三、硬件设计阶段复盘

### 设计上如果重做会改进的点

1. **P0 上拉电阻阵列改用排阻**（如 8×10K 排阻），比 8 只独立电阻更整齐、更省焊接时间
2. **蜂鸣器驱动三极管加基极下拉电阻**（10K 到地），避免 MCU 复位瞬间基极悬空导致蜂鸣器误响
3. **点阵与蜂鸣器之间的地走线加宽**，并把蜂鸣器远离 MCU 的晶振区域，减少电源噪声对定时器精度的影响
4. **增加一个串口测试点**，调试时能用串口助手打印状态，不必依赖点阵显示
5. **预留一组可外接的排针**，方便后续接示波器测波形

## 四、STM32F411 平台搭建阶段（2026-10-18 ~ 10-21）

> 这是音乐盒之后的第二个平台（Cortex-M4）。这一段的问题**与 8051 完全无关**，
> 但恰恰是最能体现"跨平台迁移能力"的部分 —— 同一类问题在两个架构上表现完全不同。

### 问题 8：CubeIDE 报 "No ST-LINK detected"，但 ST-LINK 明明插着

- **现象**：CubeIDE 点 Debug 立刻弹出 `No ST-LINK detected: Please connect ST-LINK and restart the debug session`
- **环境**：WeAct STM32F411CEU6 V3.0 + ST-Link V2，STM32CubeIDE 2.2.0
- **排查过程**：
  1. 先查 Windows 设备管理器 —— `STM32 STLink`（VID_0483&PID_3748）状态 **OK**
  2. 查是否有程序占用 —— 只有 CubeIDE 本身，**CubeProgrammer 当时没开**
  3. 改用 **STM32CubeProgrammer 单测**：选 `ST-LINK` 接口 → `Connect`
     → **成功**，识别到 `STM32F411xC/E`，Device ID `0x431`，固件 `V2J37S7`
  4. 既然 CubeProgrammer 能连上，说明 **ST-LINK 硬件和芯片都没问题**
  5. 于是转向查 CubeIDE 的工程配置 → 发现 `.ioc` 文件里 **`Mcu.Pin` 列表只有 PH0/PH1/PA9/PA10/PA13/PA14，根本没有 PC13**
- **根本原因**：**报错信息是误导性的。** CubeIDE 启动调试时会做一次工程配置校验，
  `.ioc` 与实际 MCU 配置不匹配时，它用一个泛化的"No ST-LINK detected"来报 —— 实际跟 ST-LINK 毫无关系
- **解决方法**：在 `.ioc` 里补上 PC13 的 GPIO 配置
  ```
  Mcu.IP0=GPIO          ← 原本连 GPIO 这个 IP 项都没有
  Mcu.Pin7=PC13
  PC13.Mode=GPIO_Output
  PC13.Signal=GPIO_Output
  PC13.GPIO_Label=LED_PC13
  ```
- **收获**：
  - **报错信息要验证，不要盲信。** 同一个错误可能来自完全不同的原因
  - **换一个工具复现是最快的定位手段** —— CubeProgrammer 能连上，就说明问题在 CubeIDE 侧
  - "工程配置校验失败"被包装成"硬件未连接"，这种设计在嵌入式工具里很常见

### 问题 9：烧录成功，但程序"不跑"

- **现象**：用 CubeProgrammer 烧录 `.elf` 后，LED 不亮。**关掉 CubeProgrammer 窗口后，LED 立刻开始正常闪烁**
- **排查过程**：
  1. 怀疑固件没烧进去 → 看 CubeProgrammer 日志，显示 `文件下载完成`、校验通过
  2. 怀疑代码有问题 → 检查发现程序逻辑正确
  3. 关键观察：**现象与"关掉调试器"强相关** → 方向转向调试器行为
- **根本原因**：**CubeProgrammer 连接芯片时会自动把 CPU 置于 halt（暂停）状态**，
  这是调试器的标准行为（要准备接收断点、读寄存器、显示变量）。
  **CPU 被暂停 → 你的程序根本没在执行 → LED 当然不闪。**
  关闭调试器 → 芯片复位并从 Flash 启动 → 程序开始运行
- **解决方法**：
  - 方案 A：下载完成后点 CubeProgrammer 右上角绿色 **▶ Run** 按钮
  - 方案 B：下载完直接**断开连接**（断开时调试器会复位芯片），效果相同
- **收获**：
  - **"程序不跑"的第一反应应该是"是不是被调试器 halt 了"**，而不是"代码写错了"
  - 这个坑在换环境、换工具时随时会再遇到（VS Code 插件、OpenOCD、Keil 调试器同理）

### 问题 10：F411 没有 BRR 寄存器，编译直接报错

- **现象**：写 `GPIOC->BRR = (1 << 13);` 编译报
  `error: 'GPIO_TypeDef' has no member named 'BRR'; did you mean 'BSRR'?`
- **排查过程**：
  1. 查 `stm32f411xe.h` 里的 `GPIO_TypeDef` 定义 → 确认成员只有
     `MODER / OTYPER / OSPEEDR / PUPDR / IDR / ODR / BSRR / LCKR / AFR[2]`，**没有 BRR**
  2. 回想 51 项目的经验 —— F1 系列有独立的 BRR 寄存器，**F4 取消了它**
- **根本原因**：**F4 系列把 BRR 的功能并进了 BSRR 的高 16 位**
  ```
  BSRR 的 bit0~15   →  置位 ODR  →  输出高电平
  BSRR 的 bit16~31  →  复位 ODR  →  输出低电平
  ```
  F1 的 `BRR = 1`（输出低）对应 F4 的 `BSRR = 1 << 16`
- **解决方法**：F411 输出低电平要写
  ```c
  GPIOC->BSRR = (1 << (16 + 13));   /* bit29 → 复位 → PC13 输出低 */
  ```
- **收获**：
  - **寄存器定义跨型号不能想当然。** 从 F1 抄到 F4，这里必踩
  - 写寄存器代码前先翻头文件确认成员名，比抄教程可靠
  - **F411 没有 BRR，但有 `HAL_GPIO_WritePin` 可以屏蔽这个差异** —— HAL 库帮你做了型号适配，这也是用 HAL 的价值之一

### 问题 11：PC13 配了输出也不亮 —— 忘了开时钟

- **现象**：`.ioc` 里 PC13 配成 `GPIO_Output`、`MX_GPIO_Init()` 里也调了 `HAL_GPIO_Init()`，但 LED 死活不亮
- **排查过程**：
  1. 检查 MODER 配置 —— 正确
  2. 检查 BSRR 写法 —— 正确
  3. 检查 `MX_GPIO_Init()` → **发现只开了 `GPIOH_CLK` 和 `GPIOA_CLK`，没有 GPIOC**
- **根本原因**：**STM32 的所有外设上电默认断电**，时钟信号就是外设的电源开关。
  GPIOC 的时钟没开，往 `GPIOC->MODER` 里写值等于往一个断电的模块写 —— 写不进去
- **解决方法**：
  ```c
  __HAL_RCC_GPIOC_CLK_ENABLE();                    /* HAL 方式 */
  RCC->AHB1ENR |= (1 << 2);                       /* 寄存器方式，GPIOC 在 AHB1 bit2 */
  ```
- **收获**：**"配了寄存器但外设不工作"是嵌入式第一大坑，原因永远是时钟。**
  外设初始化的第一步永远是开时钟 —— 这条已经写进我的调试清单里了

### 问题 12：主循环里有个 `while(1)` 把后面的代码全锁死了

- **现象**：串口 `printf` 完全没有输出，但 UART 初始化代码明明写了
- **排查过程**：
  1. 检查 `MX_USART1_UART_Init()` 有没有被调用 → **发现它被写在了另一个 `while(1)` 之后**
- **根本原因**：main 函数里有**两个 `while(1)`**。第一个在做 LED 翻转，
  它是死循环，**后面的 UART 初始化和第二个 while 永远执行不到**
- **解决方法**：合并成一个主循环，把 LED 翻转和串口打印都放进去
- **收获**：**一个函数里有多个 `while(1)` 一定是 bug。** 改代码时要养成"一个入口、一个出口循环"的习惯
  —— 这跟之前修的"曲末越界"是同一类问题：**看起来能跑，其实是运气好**

## 五、踩过的坑清单（速查）

### 8051 平台

| 坑 | 原因 | 解决 |
|---|---|---|
| 点阵不亮 | P0 开漏无上拉 | 外接 10K×8 上拉电阻阵列 |
| 蜂鸣器声音小有杂音 | 引脚直接驱动电流不足 | 加三极管 + 1K 基极电阻 |
| 曲末越界 | `sizeof(数组)` 是字节数 | 除以 `sizeof(数组[0])` |
| 程序随机跑飞 | 常量表未加 `code` 撑爆 128B RAM | 常量表加 `code` |
| 音调不准 | 漏算 8051 的 12 分频 | 时基公式乘 12 |
| 音调偶尔飘 | ISR 里混入显示刷新 | ISR 只做翻转与重装载 |
| Keil 找不到文件 | 工程文件相对路径失效 | 改为 `..\User\main.c` |
| 切歌时按键无响应 | 在等待音符的长循环里没检查标志位 | 加 `need_break` 打断标志 |

### STM32F411 平台

| 坑 | 原因 | 解决 |
|---|---|---|
| CubeIDE 报 No ST-LINK detected | **.ioc 里没配 PC13**，工程配置校验失败 | 补齐 `.ioc` 的 GPIO 配置 |
| 烧录后程序不跑 | **调试器把 CPU halt 了** | 点 Run 或断开连接 |
| 编译报没有 BRR | **F4 取消 BRR，并进 BSRR 高 16 位** | `BSRR = 1 << (16 + pin)` |
| 配了输出 LED 仍不亮 | **没开 GPIOC 时钟** | `RCC->AHB1ENR \|= (1 << 2)` |
| 串口没输出 | main 里有**两个 while(1)**，第二个永远到不了 | 合并成一个主循环 |
| 调试时程序不响应 | 忘了调试器处于 halt 状态 | 先点 Run 确认程序在跑 |
